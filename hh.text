Phase 5 — Amazon S3 Integration
This phase swaps local disk storage (Phase 4) for real S3 storage. The file metadata workflow (database rows, ownership checks, API shape) doesn't change at all — only where the actual file bytes live changes. This is exactly why we built the storagePath column back in Phase 3 without using it yet: it was designed to eventually hold an S3 key instead of a local filename, with no schema change needed now.

Important heads-up before we start: any files you uploaded during Phase 4 testing are sitting on your local disk, referenced by local filenames in storagePath. Once we switch to S3, the code will look for files in S3 using that same column — so those old test rows will fail to download (404) since their storagePath values aren't valid S3 keys. For a learning project with test data, the simplest fix is: delete those old test rows (via the dashboard's delete button, or directly in MySQL) and re-upload fresh test files after this phase is done. I won't write a migration script for this unless you want one — let me know if your test data actually matters to you.

Part A — AWS setup (console work, not code)
1. Create an S3 bucket
Log into the AWS Console, go to S3.
Click Create bucket.
Bucket name: something globally unique, e.g. cloudvault-documents-<yourname>.
Region: pick one close to you, e.g. us-east-1. Remember this — it goes in .env.
Leave "Block all public access" checked (enabled) — your documents are private; nobody should be able to guess a URL and download someone's file. We'll use temporary signed URLs instead (explained below).
Leave everything else default, click Create bucket.
2. Create an IAM user with least-privilege access
Rather than using your root AWS account credentials (never do this) or granting full S3 access, we'll create a dedicated user that can only touch this one bucket.

Go to IAM → Users → Create user.
Name it something like cloudvault-backend.
Skip "console access" — this user only needs programmatic (API) access, not console login.
Under permissions, choose Attach policies directly → Create policy → JSON tab, and paste:


json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:PutObject",
        "s3:GetObject",
        "s3:DeleteObject"
      ],
      "Resource": "arn:aws:s3:::cloudvault-documents-<yourname>/*"
    }
  ]
}
Replace cloudvault-documents-<yourname> with your actual bucket name.

Why this specific policy, not AmazonS3FullAccess: this user can only upload, download, and delete objects inside this one bucket — it can't list, create, or delete other buckets, or touch any other AWS service. If these credentials were ever leaked, the damage is contained to this one bucket's file contents.

Name the policy (e.g. CloudVaultS3Access), create it, then attach it to the cloudvault-backend user.
Go to the user → Security credentials tab → Create access key → choose "Application running outside AWS" → create it.
Copy the Access Key ID and Secret Access Key immediately — AWS only shows the secret once.

4. Switch multer from disk storage to memory storage
Update backend/src/middleware/upload.js:



javascript
const multer = require('multer');
const path = require('path');

// Minimal denylist — blocks obviously executable file types.
const BLOCKED_EXTENSIONS = ['.exe', '.bat', '.cmd', '.sh', '.msi', '.com', '.scr', '.js', '.vbs', '.ps1'];

// memoryStorage keeps the uploaded file in RAM as a Buffer (req.file.buffer)
// instead of writing it to local disk. We then upload that buffer directly
// to S3 in the controller — the file never touches this server's disk at all.
const storage = multer.memoryStorage();

const fileFilter = (req, file, cb) => {
  const ext = path.extname(file.originalname).toLowerCase();
  if (BLOCKED_EXTENSIONS.includes(ext)) {
    return cb(new Error('FILE_TYPE_NOT_ALLOWED'), false);
  }
  cb(null, true);
};

const upload = multer({
  storage,
  fileFilter,
  limits: { fileSize: 20 * 1024 * 1024 }, // 20 MB
});

module.exports = upload;
What changed and why: multer.diskStorage({...}) (with its destination/filename functions writing to your local uploads/ folder) is replaced with multer.memoryStorage() — a one-line swap. Now req.file.buffer holds the raw file bytes in memory, which the controller uploads straight to S3, rather than req.file.filename pointing at a path on your server's disk. The fileFilter and size limit logic are completely unchanged — those rules don't care where the file ends up.

5. Update the controller — upload, download, and delete now talk to S3
Replace backend/src/controllers/fileController.js:



javascript
const { PutObjectCommand, GetObjectCommand, DeleteObjectCommand } = require('@aws-sdk/client-s3');
const { getSignedUrl } = require('@aws-sdk/s3-request-presigner');
const pool = require('../config/db');
const s3Client = require('../config/s3');
const { classifyFileType } = require('../utils/fileType');

const BUCKET_NAME = process.env.AWS_S3_BUCKET_NAME;

function formatFileSize(bytes) {
  if (bytes < 1024) return `${bytes} B`;
  if (bytes < 1024 * 1024) return `${(bytes / 1024).toFixed(0)} KB`;
  if (bytes < 1024 * 1024 * 1024) return `${(bytes / (1024 * 1024)).toFixed(1)} MB`;
  return `${(bytes / (1024 * 1024 * 1024)).toFixed(2)} GB`;
}

function toApiShape(row) {
  return {
    id: row.id,
    name: row.name,
    type: row.type,
    size: formatFileSize(row.sizeBytes),
    uploadedAt: row.createdAt,
  };
}

// GET /api/files
const listFiles = async (req, res) => {
  try {
    const { userId } = req.user;

    const [rows] = await pool.query(
      'SELECT id, name, type, sizeBytes, createdAt FROM File WHERE userId = ? AND isDeleted = 0 ORDER BY createdAt DESC',
      [userId]
    );

    return res.status(200).json({ files: rows.map(toApiShape) });

  } catch (error) {
    console.error('List files error:', error);
    return res.status(500).json({ message: 'Something went wrong while fetching your files.' });
  }
};

// GET /api/files/:id
const getFile = async (req, res) => {
  try {
    const { userId } = req.user;
    const { id } = req.params;

    const [rows] = await pool.query(
      'SELECT id, name, type, sizeBytes, createdAt FROM File WHERE id = ? AND userId = ? AND isDeleted = 0 LIMIT 1',
      [id, userId]
    );

    const file = rows[0];
    if (!file) {
      return res.status(404).json({ message: 'File not found.' });
    }

    return res.status(200).json({ file: toApiShape(file) });

  } catch (error) {
    console.error('Get file error:', error);
    return res.status(500).json({ message: 'Something went wrong while fetching the file.' });
  }
};

// POST /api/files — uploads the file buffer (from multer's memoryStorage) to S3
const uploadFile = async (req, res) => {
  try {
    const { userId } = req.user;

    if (!req.file) {
      return res.status(400).json({ message: 'No file was uploaded.' });
    }

    const type = classifyFileType(req.file.originalname);

    // A unique S3 object key, namespaced per user, so two users' files
    // never collide even if they upload files with identical names.
    const s3Key = `users/${userId}/${Date.now()}-${Math.round(Math.random() * 1e9)}-${req.file.originalname}`;

    await s3Client.send(
      new PutObjectCommand({
        Bucket: BUCKET_NAME,
        Key: s3Key,
        Body: req.file.buffer,
        ContentType: req.file.mimetype,
      })
    );

    const [result] = await pool.query(
      'INSERT INTO File (userId, name, type, sizeBytes, storagePath) VALUES (?, ?, ?, ?, ?)',
      [userId, req.file.originalname, type, req.file.size, s3Key]
    );

    const [rows] = await pool.query(
      'SELECT id, name, type, sizeBytes, createdAt FROM File WHERE id = ? LIMIT 1',
      [result.insertId]
    );

    return res.status(201).json({
      message: 'File uploaded successfully.',
      file: toApiShape(rows[0]),
    });

  } catch (error) {
    console.error('Upload file error:', error);
    return res.status(500).json({ message: 'Something went wrong while uploading the file.' });
  }
};

// GET /api/files/:id/download — returns a temporary signed S3 URL, not the file itself
const getDownloadUrl = async (req, res) => {
  try {
    const { userId } = req.user;
    const { id } = req.params;

    const [rows] = await pool.query(
      'SELECT name, storagePath FROM File WHERE id = ? AND userId = ? AND isDeleted = 0 LIMIT 1',
      [id, userId]
    );

    const file = rows[0];
    if (!file || !file.storagePath) {
      return res.status(404).json({ message: 'File not found.' });
    }

    const command = new GetObjectCommand({
      Bucket: BUCKET_NAME,
      Key: file.storagePath,
      // Forces the browser to download with the ORIGINAL filename,
      // not the s3Key (which includes the userId/timestamp prefix).
      ResponseContentDisposition: `attachment; filename="${file.name}"`,
    });

    // Signed URL valid for 60 seconds — long enough for the browser to
    // start the download, short enough that a leaked/logged URL becomes
    // useless almost immediately.
    const url = await getSignedUrl(s3Client, command, { expiresIn: 60 });

    return res.status(200).json({ url });

  } catch (error) {
    console.error('Get download URL error:', error);
    return res.status(500).json({ message: 'Something went wrong while preparing the download.' });
  }
};

// DELETE /api/files/:id — removes the database row AND the object in S3
const deleteFile = async (req, res) => {
  try {
    const { userId } = req.user;
    const { id } = req.params;

    const [rows] = await pool.query(
      'SELECT storagePath FROM File WHERE id = ? AND userId = ? LIMIT 1',
      [id, userId]
    );

    const file = rows[0];
    if (!file) {
      return res.status(404).json({ message: 'File not found.' });
    }

    await pool.query('DELETE FROM File WHERE id = ? AND userId = ?', [id, userId]);

    if (file.storagePath) {
      try {
        await s3Client.send(
          new DeleteObjectCommand({ Bucket: BUCKET_NAME, Key: file.storagePath })
        );
      } catch (s3Error) {
        // Same reasoning as Phase 4's fs.unlink: don't fail the whole
        // request over S3 cleanup — the database row (source of truth)
        // is already gone. Log it so it's visible for debugging.
        console.error('Could not remove object from S3:', s3Error.message);
      }
    }

    return res.status(200).json({ message: 'File deleted.' });

  } catch (error) {
    console.error('Delete file error:', error);
    return res.status(500).json({ message: 'Something went wrong while deleting the file.' });
  }
};

module.exports = { listFiles, getFile, uploadFile, getDownloadUrl, deleteFile };
Explaining what changed and the key S3 concepts:

S3 "key" vs. local "filename" — in S3, there's no real folder structure, just flat object keys that look like paths. users/${userId}/${timestamp}-...-${originalname} namespaces every file under its owner's ID — this means even if S3's access policy ever had a bug, file paths aren't predictable/guessable across users.
PutObjectCommand — the S3 SDK's upload operation. Body: req.file.buffer is the actual file bytes multer kept in memory; ContentType: req.file.mimetype tells S3 (and later, browsers) what kind of file this is.
Why download returns a URL, not the file itself (biggest conceptual change from Phase 4): in Phase 4, your Express server read the file off its own disk and streamed it directly in the response (res.download). With S3, the file doesn't live on your server anymore — it lives on Amazon's infrastructure. The standard pattern is a presigned URL: your backend asks AWS "generate a temporary, signed link that's allowed to fetch this one private object for the next 60 seconds," and hands that URL to the frontend. The browser then downloads directly from S3 — your Express server is no longer in the data path at all, which is both faster and reduces load on your server.
ResponseContentDisposition — without this, S3 would serve the file using its raw object key as the filename (ugly, includes the users/3/1696... prefix). This parameter overrides that, so the browser's save dialog shows the clean original name.
expiresIn: 60 — the signed URL stops working 60 seconds after being generated. This limits the window in which a leaked/logged URL could be misused — plenty of time for a browser to start a download, far too short to be useful to anyone who intercepts it later.
getFile and listFiles are completely untouched — they only ever dealt with metadata (name, type, size, date) from MySQL, never with file content, so nothing about S3 changes them at all. This is exactly why separating "metadata in MySQL" from "content in storage" back in Phase 3 was the right call.

Now that S3 directly serves the file (with the correct filename baked into the signed URL), the frontend's job shrinks to "ask the backend for a URL, then go to it." window.location.href = url triggers the browser's normal download behavior.

(You can also remove the unused name parameter from onDownload={handleDownload} wherever it's referenced, though leaving it doesn't cause errors — it's just unused now since the filename is embedded server-side in the signed URL.)

How to test
Make sure .env has valid AWS credentials and restart the backend.
Delete your Phase 4 test files first (via the UI's delete button, or in MySQL), since their storagePath values point to local disk, not S3 — they will 404 on download now.
Go to /files, click Upload, choose a real file, upload it.
Verify it actually landed in S3: go to the AWS Console → S3 → your bucket → you should see a new object under users/<your-id>/....
Click the file's ⋮ menu → Download → should trigger a real browser download, with the correct original filename, content intact when opened.
Verify the local uploads/ folder is no longer being used — open a fresh file, and confirm nothing new appears in backend/uploads/ (it should stay empty/unchanged from here on).
Click Delete on the file → confirm → file disappears from the list, and disappears from the S3 bucket in the AWS console.
Try accessing a signed URL manually: grab the url value from a network request to /api/files/:id/download (DevTools → Network tab), paste it into a new browser tab — it should work immediately, but wait over 60 seconds and try again — it should now fail (URL expired), confirming the security behavior works as designed.
Try uploading an oversized or blocked file type again — should still show the same validation errors as Phase 4, confirming fileFilter/limits logic survived the storage-engine swap untouched.
